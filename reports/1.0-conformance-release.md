# Axiom 1.0 — Conformance Release

*Maintainer artifact. Not shipped.* Version `1.0.0-rc.1`.

## What ships

`@cynodia/axiom-server` publishes the runtime-neutral conformance corpus and its schemas
through the package `exports` map — no monorepo clone required:

```
@cynodia/axiom-server/conformance            → the root manifest
@cynodia/axiom-server/conformance/<name>.json → one root-tier fixture
@cynodia/axiom-server/conformance/<area>/     → a per-area sub-tier + its manifest
@cynodia/axiom-server/schema/server-ir.v1..v9.schema.json, protocol.v1.schema.json
```

Reference runners are exported from `@cynodia/axiom-server`:
`runConformanceFixture` / `runConformanceSuite` (root), plus
`runQueryConformanceFixture`, `runMigrationConformanceFixture`,
`runCoordinationConformanceSuite`, `runLiveQueryConformanceFixture`,
`runWorkflowConformanceFixture`, `runAuthorizationConformanceFixture`,
`runNormalizationConformanceFixture` (sub-tiers). Each is pure over its fixture data.

`scripts/run-conformance.mjs` (`npm run conformance:run`) runs the root tier through the
**public** API only — the "held to the same standard by an outside caller" demonstration.
Ran green this pass: **46/46**.

corpus as published with `1.0.0`. The internal fixture-format generation numbers

## Result schema (spec §19)

The reference runners return `{ name, ok, failures[] }` (root) or `{ name, passed,
failures[] }` (sub-tiers). Spec §19 wants a richer stable schema distinguishing
`MATCH` / `MISMATCH` / `UNSUPPORTED` / `INVALID_FIXTURE` / `HARNESS_ERROR`, with
`expected` / `observed` / `classification` / `capability`. Formalising that machine result
type and a per-runtime `axiom.conformance.result.v1` is a **campaign item** (spec §19, §88).

## Required before `1.0.0` (campaign)

- Publish a machine-readable **fixture manifest** with the fields in spec §18
  (portable/nonportable status, expected-observation type, diagnostic strictness, minimum
  contract version).
- Formalise the result schema (§19).
- Document conformance evolution within `1.x` (§20): patch may add regression fixtures for
  already-defined behavior; a fixture imposing a *new* requirement is not patch-level.
- A standalone conformance package or documented download so a third-party runtime author
  never clones the monorepo (§17).
