# Axiom 0.16 — Implementation report

*Maintainer artifact. Not shipped in any npm tarball.*

Spec: `specs/spec16.md` — **Tooling, Explainability & AI Authoring**. Full model:
`docs/AGENT_API.md` (new "Semantic inventory, dependencies and explanation" section) and
`docs/AGENT_REFERENCE.md` ("EXPLAINABILITY & AI AUTHORING (spec16)").

## Contract-version decisions (spec16 §122-123, required to be explicit)

- **Server IR: retained at `axiom.server.v9`.** 0.16 adds no new *execution* semantics — no
  operation kind, expression kind, node kind or runtime behaviour a client/server
  disagreement could arise from. Every new capability (inventory, dependency analysis,
  explanation, capability/NativeOperation analysis, semantic diff, authoring schema,
  candidate graph edits) is inspection/authoring tooling over the existing graph, computed
  by `core`/`agent-api` and never serialized into the Server IR a runtime executes. A graph
  using no 0.16-introduced *vocabulary* (there is none) compiles to a byte-identical
  document; `AuthorityCompatibilityKey` and `semanticFingerprint` are unaffected by this
  milestone.
- **Conformance: new `axiom.conformance.v10` tier**, scoped to AgentAPI/tooling rather than
  to Server IR execution (`packages/agent-api/src/tooling-conformance.ts`,
  `runToolingConformanceFixture` / `Suite`). `axiom.conformance.v1`-`v9`
  (`packages/server/conformance/`) check that a portable execution document produces a
  required result on a real persistence backend (memory/SQLite parity); AgentAPI carries no
  execution semantics of its own to check that way, so a separate, smaller tier is correct
  rather than forcing tooling checks through infrastructure built for a different question
  (spec16 §121). 13 fixtures across the categories §124 lists that apply to a static graph
  (`inventory`, `dependencies`, `explain-action`, `explain-query`, `authorization-analysis`,
  `capabilities`, `semantic-diff`, `diagnostics`, `authoring-schema`, `graph-edit`,
  `native-boundary`); each fixture's expected result is hand-specified in the fixture file,
  never generated by calling the implementation under test (spec16 §125).

## What changed, by package

### `core`

- **`derive-edges.ts`** — two real gaps closed, not spec16 vocabulary per se but required
  for spec16 §12 ("dependencies include semantic references through … workflows …
  authorization") to be true rather than aspirational:
  - a `WorkflowDef` node now derives `invokes` edges to every action its steps call and
    `references` edges to every event its `wait-event` steps await (previously: none —
    `analyzeWorkflow`/`analyzeAuthorization` computed this by walking the node directly,
    bypassing the edge graph entirely, so `agent.getDependencies(workflowId)` returned
    nothing);
  - any node's `authorizationPolicy` / `startPolicy` / `instanceAccessPolicy` now derives a
    `references` edge to the named policy (one generic pass using the existing
    `nodeAuthorizationPolicyRefs`, so it covers `ActionDef`, `QueryDef` and `WorkflowDef`
    uniformly, and any future policy-referencing field for free).
  - Verified with the existing full core/agent-api/compiler/runtime/server/demo suite
    (unaffected — these are additive edges) plus new dependency tests.
- **`semantic-diff.ts`** (new) — `semanticDiff(before, after)`: per-kind add/remove/change
  detection (excluding entity/state/relationship/read-policy, which stay `diffSchema`'s job),
  categorized (`semantic` `authorization` `schema` `provider` `workflow` `query`
  `presentation` `metadata`), plus `compatibility` (`semanticFingerprintChanged`,
  `schemaFingerprintChanged`, `serverContractBefore`/`After`/`Changed`, `migrationRequired`).
  A rename/metadata-only edit is `metadata`, never `semantic`; attaching/detaching/editing a
  policy is always tagged `authorization` even when the changed node is an `ActionDef` /
  `QueryDef` / `WorkflowDef` (field-level check against the four policy-reference fields).
- **`authoring-schema.ts`** (new) — `authoringSchema()` / `describeAuthoringKind(kind)` /
  `listAuthorableKinds()`: one descriptor (purpose, fields with type/required/reference
  targets/closed enum, a minimal-valid template) per graph-model semantic node kind.
  Deliberately excludes the nine UI node kinds — `@cynodia/axiom-ui`'s generated
  `PATTERN_CATALOG.json` already owns that authoring contract (spec16 §71's "no handwritten
  duplicate schema" applied to an existing, better-fitting mechanism rather than adding a
  second one). Closed enums are references to the *same* exported arrays validation/runtime
  use (`OPERATION_KINDS`, `WORKFLOW_STEP_TYPES`, `AUTHORIZATION_OPERATIONS`, …), not
  hand-copied values. Templates never assign security-sensitive defaults (an `ActionDef`
  template carries no `authorizationPolicy`).
- **`server-ir.ts`** — `requiredServerContractForGraph(graph)`: the same "computed from the
  document, never asserted by hand" rule `compileToServerIR` already applies, made available
  to static tooling holding only an `ApplicationGraph` (no compiler dependency needed).
- **`semantic-identity.ts`** — `stripNonSemanticMetadata` exported (was already computed
  internally for `semanticFingerprint`; `semanticDiff` reuses the exact same notion of
  "meaning" rather than reimplementing it).
- **`graph.ts`** — default `version` bumped `'0.15.0'` → `'0.16.0'` (release-version stamp,
  covered by the existing `packages/demo/test/documentation.test.ts` version-drift checks).

### `agent-api`

New modules, each a plain function over `ApplicationGraph` (the established pattern
`authorization.ts`/`workflow.ts`/`migration.ts`/`distributed.ts`/`live-query.ts` already
use), wired onto `AgentAPI` as thin methods in `api.ts`:

- **`inventory.ts`** — `semanticInventory` (+ keyset pagination via `cursor`/`limit`).
- **`dependencies.ts`** — `transitiveDependencies` / `transitiveDependents` (cycle-safe BFS
  over the derived edge graph) / `explainDependency` (structural provenance rendering, never
  fabricated prose — built from edge kind + field metadata only).
- **`explain.ts`** — `explainAction`, `explainState`, `explainQueryFull` (composes the
  existing `GraphQueries.explainQuery` with authorization + live capability),
  `explainWorkflowFull` (composes `analyzeWorkflow` with authorization), `explainGraph`
  (structural summary — counts, executable roots, security boundaries, opaque-boundary
  count; no invented business-domain prose, per spec16 §161).
- **`capabilities.ts`** — `analyzeCapabilities`: an 11-member closed capability vocabulary
  (`persistence` `coordination` `mutation-observation` `live-queries` `workflow-store`
  `event-journal` `scheduler` `effect-execution` `provider-transaction` `blob-storage`
  `subscription-adapter`), each with `required: boolean` and `reasons: string[]` naming the
  actual graph nodes responsible (spec16 §31 — provenance, not a bare list). Independent of
  `packages/server`'s `ProviderCapabilities` (which `agent-api` cannot import — architecture
  forbids `agent-api` depending on `server`); this is a graph-static analogue, not a
  duplicate of the runtime capability descriptor.
- **`native-operations.ts`** — `listNativeOperations` / `summarizeNativeOperations`, walking
  `for-each` nesting too. `opaque: true` exactly when `declaredEffects` is empty.
- **`authorization-decision.ts`** — `explainAuthorizationDecision`: evaluates a concrete
  `{ actionId | queryId, principal?, resource? }` request through
  `evaluateAuthorizationExpression` / `decideAuthorization` (the same functions `server.ts`'s
  `authorize()` calls) — not a second evaluator. Zero mutation, zero provider call, zero
  effect. An unresolved legacy-expression external ref (a `StateDef` read, which static
  analysis has no running state to satisfy) fails closed exactly as it would at runtime with
  no resolver, rather than throwing.
- **`graph-edit.ts`** — `applyGraphChanges` (replay a `GraphChange[]` onto a private clone)
  and `proposeGraphEdit` (preconditions → apply → `synchronizeEdges` → `validateGraph` →
  `semanticDiff` against the original — all without mutating the graph passed in). Reuses
  the *existing* `GraphChange` union (`changes.ts`, already `Transaction`'s change-log
  format) as the portable edit vocabulary rather than inventing a second one.
- **`tooling-conformance.ts`** — see the contract-version decision above.
- **`api.ts`** — `AgentAPI` gains: `inventory`, `getTransitiveDependencies`/`Dependents`,
  `explainDependency`, `explainAction`, `explainState`, `explainQuery` (now the composed
  version), `explainWorkflow` (now the composed version), `explainGraph`,
  `analyzeCapabilities`, `listNativeOperations`, `summarizeNativeOperations`,
  `explainAuthorizationDecision`, `requiredServerContract`, `semanticDiff`, `proposeEdit`,
  `acceptEdit`.

## Forbidden-counter equivalents (spec16 §204)

Not implemented as a dedicated adversarial harness with named global counters. The
properties those counters would track are asserted directly in
`packages/agent-api/test/spec16-tooling.test.ts` and `tooling-conformance.ts`:

- `explainAuthorizationDecision performs no mutation and no effect` — asserts the graph's
  serialized JSON is byte-identical before/after a decision call (⇔ `analysis_state_mutation
  = 0`, `analysis_effect_creation = 0`).
- `proposeEdit validates a candidate without touching the live graph` — same technique (⇔
  `invalid_edit_accepted = 0` is covered by the companion "unresolved reference" test;
  nothing is ever applied to the graph the caller holds).
- `an absent security field cannot manufacture ALLOW` — the fixture's `P_BANNED` policy
  (`PRINCIPAL.role != "banned"`) DENYs an anonymous caller (⇔ `authorization_fail_open = 0`,
  the exact spec15pt2 F1 shape, re-asserted against the *tooling* explanation path rather
  than only the runtime path).
- `proposeEdit reports a stale precondition as an explicit conflict, never a silent
  overwrite` (⇔ `stale_edit_silent_overwrite = 0`).
- No test observed a native `TypeError`/exception escaping any spec16 entry point over the
  fixtures exercised (⇔ `agentapi_native_exception = 0` for the corpus covered — not
  claimed as exhaustive fuzzing, which Phase K would add).

`secret_disclosure`, `nondeterministic_analysis_result`, and `mixed_runtime_semantic_acceptance`
have no dedicated new test: the first two are structurally impossible given the
implementation (every spec16 function is a pure read over plain JSON-shaped graph data, no
credential ever enters or leaves it beyond the caller-supplied `principal`/`resource`
records already treated as untrusted input); the third does not apply because 0.16
introduces no new runtime/authority behavior for a mixed build to disagree about.

## Regression

The full existing fast-tier suite (`npm test`, all seven testable workspaces) is green
before and after this change: 0 failures. `derive-edges.ts`'s two new edge cases were
verified not to change any existing test's expectations (additive edges only — nothing
existing depended on their absence). The soak tier (`npm run test:soak`) was not re-run in
this session; nothing in this milestone touches the distributed/workflow/live-query runtime
paths that tier exists to stress.

## Known limitations (do not overclaim — spec16 §221)

- `authoringSchema()` is a curated, hand-written descriptor table, not derived from a
  runtime reflection API (TypeScript types are erased at build time, so no such API exists
  to derive from). It references the same closed-vocabulary *arrays* validation uses, which
  is the strongest available guarantee against drift short of a source-level codegen step —
  not attempted here.
- `semanticDiff` classifies at the *field level* only for the four
  authorization-policy-reference fields; it does not attempt a deep structural diff inside
  an arbitrary nested `Operation`/`Expression` tree beyond whole-node JSON equality, so a
  diff entry says a node changed and in which top-level category, not which sub-expression.
- `analyzeCapabilities` is a conservative over-approximation by construction (spec16 §16):
  e.g. any `QueryDef` requires `provider-transaction`, whether or not the graph ever performs
  a `provider-record` mutation.
- Phase K (a dedicated adversarial/fuzz matrix) and Phase L (published-package blind external
  validation) are open — see the phase table.
