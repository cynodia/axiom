## Harness (`harnesses/provider-failure-injection.mjs`)

A real `createMemoryDataProvider` wrapped in a `FaultProvider` decorator that, per trial,
forces one boundary to fail — either a returned `{ ok:false }` `ProviderFailure` **or** a
thrown native `Error`. An action that reads via a `query` operation and then writes
server‑authoritative state is invoked through the protocol `handle()` entry point; state is
compared before/after.

| injected fault | mode | outcome | state |
| --- | --- | --- | --- |
| `query` | `{ok:false}` | action refused, `QUERY_OPERATION_FAILED` | unchanged |
| `query` | **throw** | action refused, `QUERY_OPERATION_FAILED` (native error contained → structured diagnostic) | unchanged |
| controls (no fault) ×2 | — | action commits | changed as expected |

`partialSemanticCommit = 0 · unauthorizedMutation = 0 · nativeEscape = 0 ·
controlsCommitted = 2/2`. Raw: `out/provider-failure-injection.json`.

**Scope note:** the harness's action wrote *server‑authoritative* state, so `applyMutations`
/ `loadByIdentity` / `aggregate` on the (read‑only) data provider were not on its path;
those boundaries are covered by the conformance corpus and the in‑repo suites below rather
than by this harness (recorded as INFO — a follow‑up harness with a provider‑backed
*writable* entity would exercise them directly).
